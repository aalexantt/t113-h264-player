# 音频输出排查记录

> 平台：BingPi-M2 / T113-s3
> 声卡：`card 0: audiocodec`，设备 `/dev/snd/pcmC0D0p`
> 记录时间：2026-11-25

## 一、现象

视频播放正常，但**完全没有声音**。

## 二、当前状态

| 项目 | 状态 |
|---|---|
| MP4 音轨 | 有，`mp4a`（AAC），48kHz，mdhd timescale=48000 |
| 播放器是否处理音频 | **完全没有**，只解析了 video trak |
| 板上 AAC 解码库 | `libadecoder.so` + `libaw_aacdec.so` 都在，符号齐全 |
| 声卡设备 | `/dev/snd/pcmC0D0p` 存在 |
| `aplay` / `amixer` | 都有 |
| ALSA 开发文件 | **没有** `libasound.so`（只有 `.so.2`）和 `asoundlib.h` |

**直接原因**：播放器根本没读音频轨，所以一帧 PCM 都没往声卡送。

## 三、ALSA 直连方案

因为板上没有 libasound 开发文件，交叉编译 `-lasound` 会失败。改成自己定义
内核 uapi 结构体，直接 ioctl 操作 PCM 设备。

实现见 `src/alsa_out.c`。涉及：

```
SNDRV_PCM_IOCTL_HW_PARAMS       设置格式/声道/采样率
SNDRV_PCM_IOCTL_PREPARE         进入 PREPARED
SNDRV_PCM_IOCTL_WRITEI_FRAMES   写 PCM 帧
SNDRV_PCM_IOCTL_DRAIN           排空
```

### 3.1 三个必须踩对的细节

#### 坑 1：结构体字段顺序

`struct snd_xferi` 内核定义是：

```c
struct snd_xferi {
    snd_pcm_sframes_t result;   // 内核回填实际写入帧数
    void __user *buf;
    snd_pcm_uframes_t frames;
};
```

**顺序是 result / buf / frames，不是 frames / buf / result。**
写反了不会报错，但内核读到的 `frames` 是垃圾值，表现为写入异常或无声。

#### 坑 2：所有 mask/interval 必须先填"宽松值"

这是最隐蔽的一条。

一开始把不需要的字段留空（全 0），结果 `HW_PARAMS` 一律返回 `EINVAL`。
包括 `rmask=0` 让它自己挑也不行。

原因：空的 mask 表示"不允许任何取值"，空的 interval 表示 `[0,0]` 这个区间，
内核一算发现无解就直接拒绝。

**正确做法**：先把所有 mask 置全 1、所有 interval 拉成 `[0, ~0]`，
让内核有得选，再用具体值把要固定的那几个锁死。

```c
for (i = 0; i < 3; i++)
    memset(p.masks[i].bits, 0xff, sizeof(p.masks[i].bits));
for (i = 0; i < 12; i++) {
    p.intervals[i].min = 0;
    p.intervals[i].max = ~0u;
}
/* 再把 ACCESS/FORMAT 收紧，CHANNELS/RATE 锁成具体值 */
p.rmask = 0;
```

改完之后：
```
HW_PARAMS: r=0 OK
生效 rate=48000 ch=2, buffer=512 frames, period=64
```

#### 坑 3：ioctl 号必须用真实结构体大小

`_IOWR('A', 0x11, struct snd_pcm_hw_params)` 会把 `sizeof` 编进命令字。
内核 `snd_pcm_ioctl()` 会校验大小，不一致直接 `-ENOTTY`。

排查时踩过一个弯路：在 x86_64 上算出 `sizeof = 608`，在板子（32 位 ARM）上
实际是 `604` —— 差在 `unsigned long` 的宽度（8 vs 4 字节）。
**结构体尺寸必须在目标架构上验证**，不能拿宿主机的结果下结论。

```c
/* 实测（32 位 ARM）：
 *   sizeof(snd_pcm_hw_params) = 604
 *   sizeof(snd_xferi)         = 12
 *   offsetof(rmask)           = 512
 *   offsetof(intervals)       = 260
 */
```

## 四、一个被推翻的误判（重要）

### 4.1 一度认为是 LINEOUT 没打开

排查中发现：

```
amixer -c 0 sget 'LINEOUT'
  Mono: Playback [off]
```

同时在空闲状态下读 DAPM：

```
LINEOUT:                Off  in 0 out 1
LINEOUTL Output Select: Off  in 0 out 1
DACL: ... out "DAC_SINGLE" "LINEOUTL Output Select"
```

看起来像"信号路径断了"，于是判断 `LINEOUT` 关闭是没声音的原因，
准备写启动脚本来打开它。

### 4.2 这个判断是错的

后来在**播放进行中**采样 DAPM，结果完全不同：

```
=== 播放中（第 1-2 秒）===
Playback:                On  in 1 out 6
DACL / DACR:             On  in 1 out 3
LINEOUTL Output Select:  On  in 1 out 1
LINEOUTL / LINEOUTR:     On  in 1 out 1
LINEOUT:                 On  in 2 out 1

=== 播放结束（第 3-4 秒）===
全部 Off
```

**`LINEOUT` 的开关由 DAPM 电源管理自动控制**：播放时使能，播完关闭省电。

驱动源码印证（`snd_sun50iw9_codec.c:371`）：

```c
static int sunxi_lineout_event(...)
{
    case SND_SOC_DAPM_POST_PMU:      // 播放启动
        regmap_update_bits(regmap, AC_DAC_REG,
            (0x1 << LINEOUTL_EN) | (0x1 << LINEOUTR_EN),
            (0x1 << LINEOUTL_EN) | (0x1 << LINEOUTR_EN));   // 使能
        snd_sunxi_pa_pin_enable(pa_cfg, codec_info->pa_pin_max);  // 外部功放
        break;
    case SND_SOC_DAPM_PRE_PMD:       // 播放停止
        /* 关闭 LINEOUT 和功放 */
        break;
}
```

所以空闲时 `LINEOUT [off]` 是**正常现象**，不是故障。
不要为此写脚本去强行打开——那没有意义，DAPM 会按需覆盖。

### 4.3 教训

**采样时机决定结论的正确性。** 空闲状态下读 DAPM，看到的是"全部 Off"，
很容易误判成路径断了。必须在真正播放期间采样。

上一版脚本用了 `cmd &` + `wait` 的写法，采样时播放已经结束，
读到 idle 状态，直接导致了误判。改成"后台播放 + 循环采样"后才看到真相。

## 五、当前能确认的事实

| 结论 | 证据 |
|---|---|
| 声卡能打开，参数能配 | `HW_PARAMS: r=0`，`rate=48000 ch=2 buffer=512 period=64` |
| 能写入 PCM | 写 576000 字节（3 秒）无错误 |
| 播放时 DAPM 路径全通 | 播放中 `LINEOUT: On in 2 out 1` |
| 音量不为 0 | DAC 63%、digital 100%、Soft Volume 100% |
| 功放引脚由驱动自动使能 | `snd_sunxi_pa_pin_enable()` 在 POST_PMU 调用 |

**ALSA 软件层面一切正常。**

## 六、待确认

软件通路已经验证到"能往声卡写数据、DAPM 全通"这一步。
如果仍然听不到声音，剩下的是硬件层面：

1. **喇叭没接 / 接线错** —— 检查板子上的喇叭接口
2. **喇叭需要外部供电** —— 检查功放电源
3. **输出走的是耳机口而非喇叭** —— 用 `audiotest left` / `audiotest right`
   单独测左右声道，能判断接线
4. **功放使能引脚与硬件不匹配** —— 设备树里的 `pa_pin` 配置，
   需要确认实际 GPIO 是否对得上

排查工具（都在 `tools/`）：

```bash
audiotest               # 440Hz 正弦 3 秒
audiotest 1000 5        # 1000Hz 5 秒
audiotest left          # 只左声道
audiotest right         # 只右声道
audiotest sweep 5       # 扫频 100~8000Hz
```

```bash
sh tools/probe_audio.sh # 播放期间采样 DAPM，看信号路径
```

## 七、下一步

音频输出通路打通后，还需要：

1. **mp4parse 支持音频轨** —— 目前只解析第一个 video trak，需要同时解析 audio trak
   （`hdlr=soun`、`stsd=mp4a`、`esds` 里的 AudioSpecificConfig）
2. **接 libadecoder 解 AAC** —— `CreateAudioDecoder` / `InitializeAudioDecoder` /
   `DecodeAudioStream` / `DecRequestPcmBuffer`
3. **时钟改成音频驱动** —— 现在是 PTS 自推的纯视频时钟。
   加上音频后必须以音频播放位置为主时钟，否则会持续漂移。

第 3 条最关键：音频有硬性采样率约束（写快了 underrun 断音、写慢了积压延迟），
视频帧是"可以丢可以等"的。让视频迁就音频才是正确做法。
