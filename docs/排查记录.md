# T113 硬解播放器排查记录

> 平台：BingPi-M2 / T113-s3（armv7l，musl libc）
> 固件：`tina.meetyoo.20250105.062242`，内核 `Linux 5.4.61`
> 源码包：`Tina-Linux-20250105.tar.gz`
> 记录时间：2026-11-25

## 一、问题起点

原播放器基于 `xplayer`（`libtplayer.so` → `layerControl`），播放时出现：

```
E FbmReturnPicture return fail, bUsedByRender=0
E vdecoder <picNode is full when queue buffer>
E vdecoder <NOframeBuffer:>>> return NO_FRAME_BUFFER>
```

画面卡死，解码器拿不到空闲帧缓冲。

## 二、`layerControl` 的队列问题

源码位置：`Tina-Linux/package/allwinner/liballwinner_tina/liballwinner/LIBRARY/PLAYER/layerControl/layerControl_android_newDisplay.cpp`

```c
#define NUM_OF_PICTURES_KEEP_IN_NODE (NUM_OF_PICTURES_KEEP_IN_LIST+1)  // :41
VPictureNode picNodes[NUM_OF_PICTURES_KEEP_IN_NODE];                    // :78

for(i = 0; i < NUM_OF_PICTURES_KEEP_IN_NODE; i++) {                     // :1195
    if(lc->picNodes[i].bUsed == 0) { ... break; }
}
if(i == NUM_OF_PICTURES_KEEP_IN_NODE)
    loge("*** picNode is full when queue buffer");                      // :1206
```

`NUM_OF_PICTURES_KEEP_IN_LIST` 在 `layerControl_linux.cpp:32` 定义为 **2**，即只有 **3 个节点**。G2D 流水线周转不开。

> 但这条线最终**没有走通**，也没有必要修：板上的 `libtplayer.so` 是 2022-10-12 的预编译产物，与 SDK 源码版本不完全对应（库里有 `picNode is full`，但在源码的两个 layerControl 实现里只有 android_newDisplay 有这句）。**结论是绕开它，直接调底层 vdecoder**，而不是去改这个队列。

## 三、绕开 xplayer：直接调 libvdecoder

参考实现：`D:\workspace\_More_\h618_hdmi\h618\src\video_decoder_cedar.c`（H618 平台）。

关键设计：
- 不链接 `libtplayer`，只用 `-lvdecoder -lvideoengine -lVE -lMemAdapter -lcdc_base`
- 三线程：parser 送码流 / decoder 解帧 / 主线程取帧送显
- 双帧持有，避免 disp 正在扫的缓冲被解码器复用

### 3.1 编译环境

板上**没有** gcc/make，宿主机**没有**交叉编译器，SDK 工具链是 Linux x86 二进制，最终走 WSL（Ubuntu-22.04）：

```
工具链：Tina-Linux/prebuilt/gcc/linux-x86/arm/toolchain-sunxi-musl/toolchain
        arm-openwrt-linux-gcc (OpenWrt/Linaro GCC 6.4-2017.11)
```

**关键：必须用 musl 工具链，不能用 glibc 的。**

板上只有 musl：
```
/lib/ld-musl-armhf.so.1 -> libc.so
（没有 /lib/ld-linux-armhf.so.3）
```
用 glibc 工具链编出来的 ELF 解释器是 `/lib/ld-linux-armhf.so.3`，板上一执行就是 `not found`（`ldd` 却显示正常，容易误判）。

链接用的 `.so` 从板上 `adb pull` 下来，保证 ABI 一致。

### 3.2 五个必须踩对的坑

按发现顺序记录。

#### 坑 1：`AddVDPlugin()` 必须先调

不调用时：
```
E VideoEngineCreate: unsupported format H264
E InitializeVideoDecoder: create video engine fail.
```

`AddVDPlugin()` 声明在 `vdecoder.h:267`，实现在 `libvideoengine.so`。Linux 下链接必须加 `-lvideoengine -lVE`，否则报 undefined reference。

调用后能看到：
```
I CedarPluginVDInit: register h264 decoder success!
I CedarPluginVDInit: register h265 decoder success!
```

#### 坑 2：结构体布局——新旧两版头文件差一倍

SDK 里有**两套** cedarc 头文件：

| | 旧版（2022）<br>`liballwinner_tina/LIBRARY/libcedarc/include` | 新版（2025）<br>`tina_multimedia/libcedarc/include` |
|---|---|---|
| `VConfig` | **116** 字节 | **196** 字节 |
| `VideoPicture` | **144** 字节 | **296** 字节 |
| `eOutputPixelFormat` 偏移 | 36 | 48 |
| `nDisplayHoldingFrameBufferNum` | 96 | 108 |
| `memops` | 112 | 136 |
| `ScMemOpsS` 成员数 | 17（有 `palloc_secure`，无 `open2`） | 24（有 `open2`/`get_fd_by_vir`） |

（数据是在板上跑 `of_old` / `of_new` 实测得到的，不是查文档。）

**判断板上库属于哪一版**：查 `libvdecoder.so` 的字符串表——

```
nVeFreq at ...  "%s: ... *** pVconfig->nVeFreq = %d"
houxiaoni  Fri Nov 13 10:19:03 2020 +0800  master  CedarC-v1.3.0
```

有 `nVeFreq` 字段、版本是 **CedarC v1.3.0 (2020-11-13)**，属于**新版布局**。

> 这里走过一次弯路：先试了旧版头文件，结果 `conf.nVeFreq` 编译不过（旧版 VConfig 没这字段），跑起来 `Segmentation fault`。**新版才是对的。**

#### 坑 3：`bGpuBufValid` 必须为 0

这是最隐蔽的一条。

板上 `tplayerdemo` 的 debug 日志里是 `bGpuBufValid=1`，照着设 1 之后：

```
FbmCreate, total fbm number: 12, decoder needed: 2     ← 只建结构
（然后 RequestPicture 一直报）
Fbm module of video stream 0 not create yet
```

设成 **0**：

```
FbmCreateBuffer: ** call allocate pic buf, i = 0, maxNum = 12
                 ... i = 1..11 ...
```

**缓冲才真正分配。** 原因：`bGpuBufValid=1` 是让外部通过 `SetVideoFbmBufAddress` 提供缓冲的路径，不提供就永远是 `NO_FRAME_BUFFER`。

实测返回值对照：

| bGpuBufValid | DecodeVideoStream 返回 |
|---|---|
| 1 | 4 (`NO_FRAME_BUFFER`)，一直循环 |
| 0 | 3 (`KEYFRAME_DECODED`) → 1 (`FRAME_DECODED`) |

#### 坑 4：AVCC → AnnexB 转换（且缓冲区要留够）

MP4 的 sample 是 **AVCC 长度前缀**格式，解码器要 **AnnexB 起始码**。

实测证据：
```
sample0 总长 105222，前 4 字节 = 00 01 9b 02 = 105218
105222 - 4 = 105218  ← 完全吻合，证明是 4 字节长度前缀
extradata 却是 00 00 00 01 67 ... 00 00 00 01 68（AnnexB）
```

两种都试过的返回码：

| 送什么 | DecodeVideoStream |
|---|---|
| 原始 AVCC | 5 (`NO_BITSTREAM`) |
| 转成 AnnexB | 3 → 1（正常出帧） |

**转换缓冲区容量要按 `len + len/8 + 256` 留。** 按 `len+64` 会让首帧 105KB（NAL 多）转换失败，函数返回 -1，退化成送原始数据，表现为 `NO_BITSTREAM`。

> 中间还有一个自造 bug：`di.nLength` 写在 `memset(&di,0,...)` 之前被清零，导致解码器收到 `nLength=0`。查了半天才发现是赋值顺序问题。

#### 坑 5：取 dma-buf fd 靠 memops 虚表索引 23

`VideoPicture.nBufFd` **恒为 0**，不能直接用。要从 memops 虚表取：

```c
typedef int (*fn_t)(void *);
fn_t fn = ((fn_t *)(void *)memops)[23];   // 32 位偏移 = 23*4 = 92
int fd = fn(pic->pData0);
```

结论如何验证的（`fdverify.c`）：

```
帧1: get_fd(pData0) → fd=9    readlink=/dmabuf:   fstat.size=1413120
帧2: get_fd(pData0) → fd=10   readlink=/dmabuf:   fstat.size=1413120

理论值 1280 × 736 × 1.5 = 1413120  ← 完全吻合
```

- `readlink` 是 `/dmabuf:` → 确认是 dma-buf
- `size` 与帧缓冲大小一致 → 确认对应的是这块帧
- 两帧拿到不同 fd → 确认是 per-buffer

pic#1  1280x736  pts=0     Y:mean=113.4 var=2805 min=0 max=230

## 四、送显

### 4.1 接口选择

`sunxi_display2.h` 里**没有** `DISP_CMD_VIDEO_SET_FB` / `VIDEO_START`（那是更老的接口）。只能用：

```c
DISP_LAYER_SET_CONFIG2 = 0x49
```

ioctl 协议（`dev_disp.c:1027`）：
```c
ubuffer[0] = screen_id
ubuffer[1] = &disp_layer_config2
ubuffer[2] = 层数量
```

### 4.2 屏幕尺寸

`DISP_GET_SCN_WIDTH`/`HEIGHT` 的返回值**从 ioctl 返回**，不写 ubuffer（`dev_disp.c:820`）：

```c
case DISP_GET_SCN_WIDTH:
    mgr->device->get_resolution(device, &width, &height);
    ret = width;      // ← 宽度就是返回值
```

### 4.3 四个显示问题的定位

第一版送出后：**画面变形、颜色不对（紫绿）、左右两份、没全屏**。

先用已验证的裸帧做对照——同一帧数据用正确 NV12 还原是**完全正常的照片**，所以**解码没问题，全是 disp 配置的问题**。逐个排查：

#### 问题 A：颜色错乱 + 左右重复 → 通道选错

```c
// de_feat.h: CHN_NUM=4, VI_CHN_NUM 为 1 或 2
// de_rtmx.c:
vi_chno = de_feat_get_num_vi_chns(sel);
if (channel < vi_chno)   → VI（视频）路径，支持 YUV
else                     → UI 路径，数据被当 RGB 解释
```

原来放在 `channel=1, layer=1`（UI 通道），把 NV12 当 RGB 喂进去 → 紫色乱码 + 像素重排。

**改成 `channel=0`（VI 通道）** 后颜色正确。

> `layerControl_linux.cpp:23` 的注释也印证：`channel 0 for pad screen`。

#### 问题 B：变形 → crop 用了 736 而不是 720

解码器输出 `1280x736`，736 是 720 向上对齐到 16。

实测那多出来的 16 行：`Y 均值 = 0.0`（全黑）。当成画面内容一起拉伸就变形。

- `size[]` 用 736（物理布局）
- `crop` 用 **720**（实际显示区域）

#### 问题 C：残留层叠加

反复测试会让旧层留在 disp 里：

```
ch[0] lyr[0]  新层
ch[1] lyr[0]  UI 层
ch[1] lyr[1]  上一次测试的残留层  ← 叠在一起
```

写了 `dispclean.c` 遍历 ch0~3 / lyr0~3 全部关闭。

#### 问题 D：address 不变

`/sys/class/disp/disp/attr/sys` 里 `addr[]` 不变是**正常现象**——它显示的是最近一次 SET_CONFIG2 写入的配置值。判断播放是否正常要看帧计数和 fd 轮转（`fd` 从 10→13→17 变化说明缓冲在轮转）。

### 4.4 帧率不对 → timescale 用错

现象：播放慢得多。原来代码：

```c
target = base_wall + (pts - base_pts) * 1000;   // 把 pts 当毫秒
```

**MP4 有两个 timescale：**

| 来源 | 管什么 | 本文件实际值 |
|---|---|---|
| `mvhd.timescale` | movie 的 duration | **1000** |
| `mdhd.timescale` | **该 track 里 stts/pts 的单位** | **12800** |

`stts.delta = 512`，用 mdhd 换算：`512 / 12800 = 40ms` → **25fps**。
用 mvhd 的 1000 去算：`512/1000 = 512ms` → 慢 12.8 倍。

修正：读 `mdhd`（`mp4parse.c` 里新增解析），换算公式

```c
target = base_wall + (pts - base_pts) * 1000000 / media_timescale;
```

修完实测：

```
timescale: mvhd=1000 mdhd=12800, 4271 帧 / 170840ms → 25.00 fps
已显示 300 帧 ... fps=25.0
已显示 500 帧 ... fps=25.0
```

20 秒显示 500 帧 = 精确 25fps。

## 五、OSD

### 5.1 方案

独立的 disp layer，`ARGB_8888`，`alpha_mode=0`（逐像素 alpha）。

- 背景画 `alpha=150` 的半透明黑 → 看得清但不完全挡画面
- 文字 `alpha=255` 全不透明
- 层位置：`ch1/lyr1`，`zorder=30`（高于视频的 20）

### 5.2 缓冲分配

OSD 缓冲必须是 dma-buf。用 memops 的 `palloc`（底层 ion）分配，再走索引 23 取 fd —— 和解码帧用的是同一条路径。

虚表索引（新版 24 成员布局，32 位）：
```
[4]  palloc(int size)
[6]  pfree(void*)
[23] get_fd_by_vir(void*)   ← fdverify 已验证
```

### 5.3 字体

板上没有 freetype，也不想为一个数字渲染引入库。`genfont.py` 从 `consola.ttf` 生成 1bpp 点阵表 `font.h`：

- 单元格 **9×17**，每行 2 字节，每字符 34 字节
- 覆盖 ASCII 32~126，共 95 个字符，数据量 3230 字节

### 5.4 显示内容

左上角半透明面板五行：

```
1280x720 H264          ← 实际显示分辨率 + 编码格式
fps 25.0 / 25.0        ← 实测帧率 / 目标帧率
00:12 / 02:50  x2      ← 播放时间 / 总时长 / 循环轮次
cpu 42% dec 509        ← 整机 CPU 占用 / 已解码帧数
mem 75/108M free 9M    ← 可用内存 / 总量 / 账面空闲
```

OSD 每 250ms 刷新一次，不是每帧重画（省 CPU）。

**关于内存显示的一个判断**：显示的是 `MemAvailable` 而不是 `MemFree`。

板上 `MemTotal` 只有 108MB，`MemFree` 常年在 9MB 左右，看着像内存告急。
但实际上：

```
MemTotal:      110560 kB
MemFree:         9572 kB   ← 账面空闲，小是正常的
Cached:         35292 kB   ← 空闲内存被拿去当页缓存了
MemAvailable:   77192 kB   ← 真正还能用的量
Slab:           14476 kB   ← 内核对象
SUnreclaim:      8720 kB   ← 不可回收
```

Linux 会尽量把空闲内存用作页缓存，需要时随时回收，所以 `MemFree` 低不表示内存不足。
判据应该用 `MemAvailable`。这里可用内存一直有 52MB 以上（播放时 52MB，空闲时 78MB），
全程没有内存压力。可用低于 20MB 时该行显示为红色。

**顺带排除一个误判**：一度怀疑是 `gopanel` 吃内存（dmesg 里 `total-vm:572192kB` 很吓人），
查了 `/proc/<pid>/statm` 才发现 `anon-rss` 只有 1892kB —— 那个 572MB 是**虚拟地址空间**，
不是实际占用。

同样也确认了没有"可杀的应用"：所有用户进程的实际 RSS 加起来只有约 2.4MB

| 进程 | RSS |
|---|---|
| `adbd -D` | 792 KB |
| `ntpd` | 416 KB |
| `wpa_supplicant` | 392 KB |
| `/sbin/init` | 300 KB |
| `swupdate-progress` | 204 KB |
| `sshd -D` | 156 KB |
| `led_flash` | 112 KB |
| `/bin/sh` | 32 KB |

杀任何一个都会断调试连接或断网，收益不到 2MB，没有意义。

### 5.5 验证

```
ch[0] lyr[0] z[20] fmt[76]  fb[1280,736; 640,368]  crop[0,0,1280,720]  frame[0,0,1920,1080]
ch[1] lyr[0] z[16]          fb[1920,1080]           ← 系统 fbdev 层，不能动
ch[1] lyr[1] z[30] fmt[ 0]  fb[210,111]             a[pixel 255]
```

- `fmt[76]` = `0x4c` = `DISP_FORMAT_YUV420_SP_UVUV`（NV12）
- `fmt[0]` = `ARGB_8888`
- `a[pixel 255]` 说明逐像素 alpha 生效
- `crop 1280x720` → `frame 1920x1080`，等比放大全屏

**OSD 画布只做 210×111，不是全屏。** 一开始开的是 1920×1080，
ARGB8888 要 8MB，而板子 `MemTotal` 才 108MB，压力太大。缩到面板大小后只需 91KB。

> 这里踩过一个自己造成的坑：早期版本的 `dispclean` 无差别遍历 ch0~3 / lyr0~3 全部 disable，
> 把系统的 fbdev 层（`ch1/lyr0`，zorder 16）也关了，屏幕直接黑掉，而且程序退出后也不会恢复。
> 恢复办法：`echo 0 > /sys/class/graphics/fb0/blank`。
> 现在 `dispclean` 只清视频通道 `ch0` 全部和 `ch1` 的 `lyr1~3`，保留 `ch1/lyr0`。

## 六、循环播放

### 6.1 循环时 PTS 会跳回去

parser 线程 `mp4_rewind()` 之后，PTS 从文件末尾跳回开头。
如果时钟基准不重置，`target` 会被算成"很久以前"，于是每帧都判定"落后超过 1 秒"，
触发追赶重置逻辑，表现是画面一阵乱跳。

处理办法：在 `clock_wait_us()` 里检测 PTS 回退。

```c
if (pts + (int64_t)(k->timescale / 2) < k->last_pts) {
    k->loop_count++;
    k->base_pts = pts;
    k->base_wall = now;
    k->last_pts = pts;
    k->stat_frames = 0;
    k->stat_t0 = now;
    return 0;
}
```

阈值取半个 timescale 单位（本文件 0.5 秒），足够避开 B 帧带来的小幅 PTS 乱序
（正常不超过几帧）。

### 6.2 实测结果

播放 200 秒，跨过 170.84 秒的循环点：

```
已显示 4200 帧, pts=2149888   ← 循环前
已显示 4300 帧, pts=14336     ← PTS 回退，循环触发
已显示 4400 帧, pts=65536     ← 恢复正常步进
...
已显示 5000 帧, pts=372736
```

- PTS 从 2149888 跳回 14336，**循环成功且没有卡死**
- 循环瞬间 fps 均值短暂上冲到 25.9，之后收敛回 25.0。
  这是统计窗口（`stat_frames` / `stat_t0`）被重置导致的，
  **不是播放速度异常** —— 时钟本身准确，PTS 步进稳定在 512/帧
- PTS 没回到 0 而是 14336，因为循环时解码器里还有约 28 帧旧数据缓存，
  `mp4_rewind` 后新数据接在后面。parser 和 decoder 异步，这是正常的
- 总帧数 `presented=5001`，理论 200×25=5000，误差 1 帧
- 播放结束后 `MemAvailable` 回到 78428 kB（比播放时的 52MB 更高），
  解码器和 OSD 的缓冲都正确释放，无内存泄漏

## 八、几个方法论上的教训

1. **先分清责任再改。** 画面不对时，第一步应该是把解码出的裸帧还原成图片，确认解码本身对不对。分清了"解码 vs 显示"，才不会两头瞎改。

2. **不要顺着错误前提跑。** 中间一度认定"T113 只有 MJPEG 硬解"（是用户主动纠正的）。而 `tplayerdemo` 的历史日志里其实早有 494 次 `FRAME_DECODED` 的证据，只是当时没去查。

3. **结构体布局必须实测，不能靠读文档推断。** 新旧两版头文件大小差近一倍，靠看源码猜偏移一定错。写个 `offsetof` 程序在板上跑，10 分钟就有答案。

4. **日志里的字符串格式串不等于函数签名。** 曾因 `DecodeVideoStream` 的日志只打印 4 个参数，误判成 4 参数版本，白折腾一轮。要判断签名就反汇编或查头文件。

5. **`ldd` 正常不等于能跑。** glibc/musl 的解释器路径不同，`ldd` 能解析依赖但 exec 会 `not found`。看 `file` 输出的 interpreter 字段才准。

6. **后台启动要确认真的起来了。** 曾有"播放 5 秒就停"的现象，查下来是 `nohup ... > /data/loop.log &` 里 `/data` 目录不存在，重定向失败导致进程根本没跑起来，屏幕上那"5 秒"是上一轮残留的最后一帧。后台启动后一定要 `ps` + 检查日志文件确认。

7. **`total-vm` 不等于内存占用。** dmesg 里 `total-vm:572192kB` 看着像吃内存，实际 `anon-rss` 只有 1892kB。判断进程真实占用看 RSS，不看虚拟地址空间。

8. **杀进程之前先算收益。** 想"清理内存"时把所有用户进程 RSS 加起来才 2.4MB，而每一个都是系统必需的（`adbd` 断了就没法调试，`wpa_supplicant` 断了就断网）。先量再动手。
